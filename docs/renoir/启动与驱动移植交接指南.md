## 2. 最常用：怎么启动现成镜像

手机上按住 **电源＋音量减**，直到看到 FASTBOOT；若当前系统无响应，需要持续按到硬件重启。进入后松开，USB 连电脑。以下命令不要求 Android 的 ADB 在线。

```bash
cd /home/daimile/桌面/ios-renoir
fastboot devices
sha256sum artifacts/xnu-renoir-0088/phone-power-fifo-v1/shim-boot.img
fastboot boot artifacts/xnu-renoir-0088/phone-power-fifo-v1/shim-boot.img
```

预期 SHA-256：

```text
a194831438ff3a769291d33cf71719a2d13867fc0107470fdadab3e95f5a0cc8
```

看到 `Sending ... OKAY` 和 `Booting ... OKAY`，说明镜像已经交给手机。等待数分钟观察锁屏，传输成功不代表系统一定启动成功。

**`fastboot boot` 是临时启动，每次重启后需要重新执行。** 它把镜像送到内存执行，不会把它安装进 boot 分区。iOS 文件已经在 userdata，所以日常换内核无需重新刷 root。

现成镜像选择：

| 用途 | 相对路径 | 真机状态 |
| --- | --- | --- |
| 推荐基线，时间正确、按键有效、10Hz | `artifacts/xnu-renoir-0088/phone-power-fifo-v1/shim-boot.img` | 用户确认反馈明显改善 |
| 对照，按键有效、30Hz 拷贝 | `artifacts/xnu-renoir-0084/phone-keys-v1/shim-boot.img` | 全部实体按键有效，但很慢 |
| 旧 GUI 基线，无按键/触控 | `artifacts/xnu-renoir-0083/phone-ios-identity-v3/shim-boot.img` | 锁屏已验证 |
| 读日志用的临时 recovery | `downloads/recovery/twrp-3.7.0_11-0-renoir.img` | TWRP、root ADB 已验证 |

`payload.bin`、`renoir.adt`、`kernel.development.sweet` 都不是直接给 fastboot 的文件。给 fastboot 的是包装好的 **shim-boot.img**。

不要执行 `fastboot flash boot` 来“安装”这些实验镜像。不要为了调试擦除 userdata、修改 GPT 或刷 xbl/abl。EDL 路径尚未实测，相关风险此前已明确接受，但不能把它写成“已验证能救砖”。

## 3. 怎么读取手机里的 XNU 日志

当前 XNU/iOS 没有可用 USB ADB 驱动。iOS 运行时 `adb devices` 没设备属预期；电脑上 fastboot 的输出也不是 XNU 日志。

内核通过 `sweetlog=1` 把控制台日志周期性保存到 userdata **分区末尾约 4MiB 的保留环形区**，不是 iOS 根目录中的普通文件。最新一次崩溃可能尚未落盘，因此照片也有用。

步骤 A：让 iOS 至少运行十几秒，手动进 FASTBOOT，再临时启动 TWRP：

```bash
cd /home/daimile/桌面/ios-renoir
fastboot boot downloads/recovery/twrp-3.7.0_11-0-renoir.img
adb devices -l
```

TWRP 的正常 root ADB 通常需要等 30～100 秒。若暂时显示 `sideload`、`adb shell` 关闭，先等到 recovery 正常启动，必要时退出 TWRP 的 sideload 页面。**不要点格式化 Data，也不要刷入 recovery。**

步骤 B：确认 root，然后读取：

```bash
adb shell id
mkdir -p logs
sh src/tools/sweet-log-pull.sh "logs/ios-$(date +%Y%m%d-%H%M%S).txt"
```

预期 `id` 含 `uid=0`。脚本会生成两个文件：`.txt.bin` 是原始日志环，`.txt` 是解码文本。请一起保留。脚本只读手机分区，不格式化、不挂载、不修改 iOS。

选择刚才生成的实际文件名阅读，例如：

```bash
less logs/ios-identity-v3-lockscreen.txt
rg -n 'RENOIR KEYS|panic|BSD root|HFS|launchd|SpringBoard|backboardd|error|failed' logs/ios-identity-v3-lockscreen.txt
```

旧 identity-v3 日志里的按键仍是关闭的；查新按键事件要使用本次拉取的新文件。按键日志形如 `RENOIR KEYS: key=0 down=1`；0=电源、1=音量加、2=音量减；1=按下、0=松开。记录是否成对、是否伴随读取超时。仅靠日志行间距还不能精确衡量完整显示延迟。

步骤 C：读完后，从 TWRP 回到 fastboot，再运行 iOS：

```bash
adb reboot bootloader
# 等到手机显示 FASTBOOT，再执行：
fastboot boot artifacts/xnu-renoir-0088/phone-power-fifo-v1/shim-boot.img
```

TWRP 不能挂载这个 HFS+ /data，不代表 iOS 文件系统损坏；本项目通过原始分区读取日志。若临时启动长时间停在 Booting，重新手动进 FASTBOOT 再试，**不要因此重刷 userdata**。

## 5. 改完驱动后，怎样构建与运行

完整链路是：**原始 XNU＋补丁 → macOS CI 内核 → ADT＋内核组成 payload → shim 包装 boot v2 镜像 → fastboot 临时启动**。iOS root 是另一部分，已经在手机上，不随每次驱动修改重建。

### 5.1 代码和补丁

先读 `src/AGENTS.md`、顶部 NOTES、事实表。为新驱动创建下一编号补丁（当前下一号 0085），保留前 84 个可重现补丁。可以在应用现有补丁的树里开发，但生成 diff 时要确保它只包含新改动，并使用标准 `a/`、`b/` 路径。不要把整棵临时编译树或 Apple 用户态文件提交。

```bash
python3 tools/check-patch-series.py
python3 src/tools/validate-repo.py
git -C src diff --check
```

第一条在临时干净树严格应用整套补丁；通过不代表编译通过。编号补丁失败必须修复，不能跳过。单文件交叉编译可以提前查错，完整链接仍以 CI 为准。

### 5.2 GitHub Actions 构建内核

先将新补丁提交、push 到 `renoir/input`（或自己的新分支），再指定同一分支运行：

```bash
git -C src push origin renoir/input
gh workflow run xnu.yml -R daimile2/ios-renoir --ref renoir/input
gh run list -R daimile2/ios-renoir --workflow=xnu.yml --limit 5
```

记下本次 run 的数字 ID，等待成功。下面的 `RUN_ID` 和 `新版本目录` 必须替换成实际值，不能覆盖旧产物：

```bash

gh run download RUN_ID -R daimile2/ios-renoir -n xnu-kernel -D artifacts/新版本目录/kernel
```

内核文件名仍然是 `kernel.development.sweet`，构建目标、IOKit 匹配和启动参数仍保留 SWEET 命名。直接改成 `renoirfb_*` 不会自动生效。

### 5.3 组装手机镜像（可复制的示例）

以下示例复现旧0084按键内核（不含后来的RTC修复），创建唯一的新目录；更换驱动后，把 `kernel` 指向自己的新 CI 产物。保留当前按键和 10Hz 参数：

```bash

python3 src/tools/mkpayload.py \
  artifacts/xnu-renoir-0084/kernel/kernel.development.sweet \
  "$build_dir/renoir.adt" "$build_dir/payload.bin" \
  --cmdline "$(cat "$build_dir/cmdline.txt")"
SHIM_MODE=full DTB_PATH="$PWD/dtb/vendor-boot/vendor_boot_a.img-dtb" \
  bash src/shim/build.sh "$build_dir/payload.bin"
```

两个 `cmp` 成功时没有输出。记下目录、源码提交、内核和镜像 SHA-256；补全 manifest 后再手动进 FASTBOOT：


### 5.4 历史QEMU命令（当前按用户要求跳过）

QEMU 验证内核通用启动与定时器回归，不能验证手机 SPMI、SPI、面板或 UFS。不能把手机 `rd=ufsroot0` payload 直接拿去要求 QEMU 挂载手机 root。当前可复跑已归档的测试 payload：

```bash
export PATH="$PWD/toolchain/bin:$PATH"
python3 src/tools/qemu-sweet.py \
  artifacts/xnu-renoir-0084/qemu-payload.bin \
  artifacts/qemu-repeat-0084 \
  --secs 45 --fb-base 0xe1000000 --trap-physical-timer \
  --kernel artifacts/xnu-renoir-0084/kernel/kernel.development.sweet \
  --fail-on-panic
```

以实际归档文件为准；新内核需用 `mkadt-renoir.py --qemu` 创建测试 ADT，沿用已验证 QEMU 测试启动参数和 mockfs/测试 init 链路重新组装 payload，不能把旧 payload 通过当作新内核测试。检查 `fb.txt` 中测试 PID 1、`still alive`，同时检查 panic 和 EL2 trap；QEMU 测试 PID 1 与真实 iOS launchd 是不同里程碑。

## 6. 下一个 AI 如何移植驱动

### 6.1 先移植触控：FT3658U，GENI SPI

已确认本机是 **FocalTech FT3658U（芯片 ID 0x5652）**，不是模板 sweet 的 I2C 触控。旧 `sweet_touch.c` 不能仅改地址就启用。

关键输入：

| 项目 | 本机参数 |
| --- | --- |
| SPI SE MMIO | `0x00988000`，mode 0；DT 6MHz，Android 运行记录 12MHz |
| GPIO | SPI 20–23；reset 30；IRQ 31 |
| TLMM | 基址 `0x0f000000`；配置偏移 `0x100000 + gpio*0x1000`，IO 再加 4 |
| 时钟 | Shima GCC 基址 `0x00100000`；`GCC_QUPV3_WRAP0_S2_CLK`，DT clock ID 72 |
| GCC 寄存器 | RCG `0x17270`，branch `0x1726c`；vote `0x52008` bit12；AHB bits6/7 |
| 电源 | PM8350C L7：官方驱动请求 3.3V；L2：1.8V |

参考文件：`toolchain/renoir-linux-reference/focaltech_spi/`、`platform/spi-msm-geni.c`、`platform/msm-geni-se.h`、`platform/gcc-shima.c`、`platform/pinctrl-shima.c`。官方参考固定提交及下载校验见 provenance。不要用另一个 `spi-geni-qcom.c` 的初始化流程代替下游 `qcom,spi-geni` 驱动，也不要使用 SM8350 的 GCC 表。

按以下阶段开发，每步单独开关、日志、产物及真机验收：

1. 只读 GENI 版本、固件协议、状态，确认 SE 已加载 SPI 固件。官方下游驱动会检查协议，不自动替你装固件。未知或非 SPI 时停止，不盲写控制寄存器。
2. 核对时钟、GPIO、复位状态和电源实际状态。若需要配置，先按官方驱动逐项实现，保存原值并明确寄存器语义；不要无依据复用 sweet 的地址。
3. 实现有超时的单次 SPI 传输，先读芯片 ID；确认持续稳定读到 `0x5652` 后再复位、配置触控或读取坐标。
4. 实现触点数据解析，先只打印按下/移动/松开，不发 HID。检查范围、触点 ID、包长、CRC、抬手；坏包不能制造幽灵触摸或永远按下。
5. 接到 `iokit/Kernel/arm/hid/SweetHID.cpp` 的 `sweet_hid_touch(finger, down, x, y)`。先检查其逻辑画布、偏移和边缘手势实现，避免重复缩放；物理面板 1080×2400，逻辑画布 1125×2436。
6. 真机验证底部上滑、连续移动、多指和抬手，再考虑中断取代轮询。驱动忙等必须有上限，不能在单核上长时间阻塞。

FocalTech SPI 参考协议：请求头 `[reg, 0xa0, len_hi, len_lo]`，3 dummy 字节，数据和 CRC16；CRC 多项式 `0x8408`、初始 `0xffff`、低字节在前；检查响应状态 `rx[3] & 0xa0`，CS 间隔 150μs、最多 3 次重试。实际偏移、长度和 ID 读取命令必须再次对照官方源码，不能仅按本段猜测。坐标还包含低位扩展，照搬普通 12 位 FTS 格式会错。

**电源前置条件**：模板 `sweet_rpmh.c` 的 RSC 基址 `0x18220000` 虽相同，renoir 的 TCS 分组是 WAKE 2、ACTIVE 3、SLEEP 3；active IDs 为 2–4，不能复用 sweet 的 0–1。CMD-db 保留内存 `0x80860000 + 0x20000`。在确定资源地址、active TCS、完成/错误状态前不要发送电源投票。能读 SPI 寄存器并不证明触控电源已打开。

### 6.2 已完成的实体按键

补丁 0084，源文件 `bsd/dev/sweet_keys.c`，通过 `sweetkeys=1` 启用。SPMI v5 observer 只读 PMIC，每 20ms 轮询，状态变化后调用 `sweet_hid_key`。

- PMK8350 SID0：Gen3 HLOS base `0x1300`，subtype `0x1305=0x09`，RT `0x1310`；bit7 电源、bit6 音量减。
- PM8350 SID1 GPIO6：按 one-based GPIO 换算，base `0x8d00`，RT `0x8d10` bit0 低有效，PPID `0x18d`。
- 不写 PMIC 配置、不清中断、不写复位寄存器。下一版触控必须保留这个已验证路径，不能重新启用旧 PM6150 按键代码。

### 6.3 时间、颜色、性能

时间：PMK8350 SID0 RTC enable `0x6146`，秒计数 `0x6148..0x614b`，小端。原始 RTC 不是当前日历时间；Android 使用 persist `/time/ats_2` 的 8 字节毫秒校准偏移。本机已只读提取到 `artifacts/time-reference/ats_2.bin`，是私有校准数据，不提交。应验证读取一致性、校准和单位后实现平台 `getGMTTimeOfDay`，不要写 RTC，也不要把今天日期硬编码。

颜色：需要实际锁屏照片，检查面板缓冲、surface 格式和通道顺序后再改。尚无证据认定红字必然由 BGRA/RGBA 导致。

性能：10Hz 用户已确认改善，作为新基线。先减少无用诊断/拷贝、测量开销，再逐项优化。启动参数 `cpus=8` 不等于 SMP 移植完成；真实拓扑为 4×A55＋4×A78，CPU 启动、GIC redistributor、定时器、缓存一致性均需逐步验证。GPU 驱动是独立的大工程，不能把 Linux Adreno 驱动直接编进 iOS 就获得 Metal。
